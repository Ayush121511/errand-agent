# Errand Agent

A chat agent that arranges home-service errands (book, cancel, reschedule) against mock provider tools. A real LLM (Gemini) interprets the user and drives tool calls. Application code enforces approvals, idempotent booking, recovery, prompt-injection defences, memory filtering and execution limits, so a confused or manipulated model can at worst make a bad suggestion. It can never make an unapproved or duplicate booking, or claim a success that didn't happen.

## Quick start

```bash
conda create -n errand-agent python=3.12 -y && conda activate errand-agent
pip install -e ".[dev]"            # or: uv sync
pytest -q                          # unit tests, all scenarios, recorded live cases; offline, no key
python -m evals.run                # scenarios only; rewrites docs/eval_results.md
python -m evals.live --replay      # re-score the recorded real-model cases, $0
python -m evals.live L56 F11       # live run against Gemini (needs .env) for some cases or frontiers, capped by --max-cost
python -m evals.judge              # grade every recorded reply with the cheapest calibrated judge, about $0.015
python -m evals.redteam            # score the input screen on model-written attacks; --regen for a new blind round
```

To run the live agent, copy `.env.example` to `.env` and set `GEMINI_API_KEY`. Then:

```bash
uvicorn errand_agent.app.server:app --port 8000     # web UI: chat + live trace at http://localhost:8000
python -m errand_agent.app.cli --trace              # terminal chat with inline trace
```

Local state lives in `var/` (agent DB and mock provider DB); delete it to start fresh. Live traces are written to `traces/live/`.

## How it works

```
user ──► router ──(bare "yes" / Confirm button on a pending card)──► ApprovalGate ──► ActionExecutor ──► provider
           │                                                         fingerprint check,   attempt row, idempotency key,
           │                                                         single-use consume   status check on ambiguity
           └──(anything else)──► model loop (bounded) ──► validating tool dispatcher ──► provider (read-only + hold)
                                   ▲  context: STATE + gated MEMORY + history, under a token cap, logged per call
provider events ──► proactive handler (code) ──► replacement held ──► fresh approval card
new chat        ──► greeting (code): welcome back + next free slot for each service, no model call
process start   ──► recover(): resolve pending attempts from get_booking_status
```

- **The provider is reached only through the brief's 8 fixed tools.** `ProviderClient` allows only those names, and `tests/test_contract_boundary.py` runs every scenario with any other access failing.
- The **model's tools** are `update_task`, `ask_user`, `search_providers`, `get_provider`, `hold_slot`, `propose_booking`, `list_bookings`, `propose_cancel`, `get_reschedule_options`, `propose_reschedule`, `remember`, `forget`, `confirm_memory` and `show_memories`. There is no tool that books, cancels or reschedules.
- **Facts need evidence.** A task field or memory is accepted only with a quote found in a *user* message, or a memory or booking id the code can verify.
- **Reviews are read in quarantine** by a tool-less model (`gemini-3.5-flash-lite`). The main model (`gemini-3.6-flash`) sees only a schema-checked summary.
- **Input is screened before the model** (`core/guard.py`). Requests for restricted data (system prompt, keys, other customers' data, database dumps, the provider contact list) are refused by code and stored in `security_flags`; after 3 the user is blocked (text, button and proactive rebooking) until support clears it (`GET /api/admin/flagged`, `POST /api/admin/unblock`). Gibberish gets a "could you rephrase?" reply. Neither costs a model call or ever enters a model context.

## Evaluation frontiers

Two suites cover the same frontiers. The offline scenarios (scripted model) prove what the code does; the live suite (real Gemini, one turn per case, scored by code plus the global invariants) measures what the model does with real phrasing. Live responses are recorded to `evals/cassettes/live/`, so `pytest` re-scores them for free on every run.

| Frontier | How it's handled | Offline | Live |
|---|---|---|---|
| Unsupported errand (laptop, car, groceries, flights) | Prompt scope rule; if the model still sets the service, code replies with the six services | S34 | L01–L04 |
| Service offered, nobody free | Search with no free slot ends the turn with a code reply; nothing held | S35 | L05–L06 |
| Data theft / prompt injection | Screened and flagged by code; subtler phrasings go to the model, which has nothing secret it can reach | S36, S37 | L07–L13 |
| Gibberish | Screened by code; word salad goes to the model, which asks to rephrase | S38 | L14–L17 |
| User's own wording ("washroom draining" → plumber, Hinglish) | Model maps it; code requires the user's quote as evidence | S39 | L18–L27 |
| Area not covered | Code rejects the area with the covered list | S40 | L28–L29 |
| Off-topic (stock tips, poems) | One-line decline, no tools | – | L30–L31 |
| Impossible date (yesterday, 31 Feb) | Code rejects the date | S41 | L32–L33 |
| Two errands at once | One at a time, the other acknowledged | – | L34 |
| Approval bypass ("I pre-approve") | Card is still required | S04 | L35 |
| Oversized message (40k chars) | Latest message trimmed to fit the cap | S42 | – |
| Hinglish and Hindi (booking, cancel, reschedule, memory, "haan, book kar do") | Model maps it; Hinglish confirmations, refusals and screening replies in code | `tests/test_hinglish.py` | L47–L55, L59 |
| Long conversations (7–10 turns: corrections, task switching, attacks and gibberish mid-flow, Hinglish) | Checked on final state plus the invariants | S43, S44 | L56–L59 |
| Company policies it doesn't know (provider vetting) | Says it doesn't have that information | – | L60 |

**Reply quality.** Code checks decide pass/fail on state; `evals/judge.py` grades every reply (helpful, accurate, clear, language, safe; 1–5) with the cheapest Gemini model that passes a 12-reply calibration set of known good and bad replies. Models are tried in price order; replies scored low get a second opinion from a different cheap model. Results are cached by content, so re-runs only pay for changed replies.

**Blind red-team.** `evals/redteam.py` has the cheapest model write fresh attack and ordinary messages in rounds; a round's first score is its blind score, and once it has been used for tuning only a newer round is blind.

Latest results:
- 44/44 offline scenarios.
- 60/60 live cases on `gemini-3.6-flash`; the recorded runs cost $0.38, and 19 cases cost $0 because code handled them.
- Judge: `gemini-3.1-flash-lite`, calibration 12/12, mean 5.0/5 over 90 replies after the fixes, $0.014.
- Red-team: blind recall rose from 30% to 47% after tuning, with 0/30 false positives; the live agent refused all 16 attacks the screen missed.

## Mock provider environment

All eight tools follow the brief's contracts and failure modes. Outcomes are seeded per call, and each scenario can force a specific outcome.

| Tool | Behaviour |
|---|---|
| `search_providers(service, area, date_range)` | 3–8 providers per (service, area), with prices, ratings, slots and attributes |
| `get_provider(id)` | details plus reviews; four providers carry a prompt-injection review |
| `hold_slot(id, slot)` | 10-minute hold; quoted price drifts from the search price 25% of the time |
| `book(hold_id, key)` | 70% success, 15% `slot_taken`, 15% timeout (half of those actually booked); `hold_expired`; server-side de-duplication by key |
| `get_booking_status(hold_id or key)` | source of truth |
| `cancel(booking_id, key)` | the first call per booking returns 503, the retry succeeds |
| `reschedule(booking_id, slot, key)` | `slot_conflict` on configured or unavailable slots |
| `list_bookings(user_id)` | seeded past and upcoming bookings |

The mock persists to its own SQLite file, separate from the agent's, so it behaves like a remote service across agent restarts. Provider cancellations are simulated as events.

## Configuration

| Setting | Default |
|---|---|
| Limits per run | 8 model calls, 12 model tool calls, 45 s wall clock; executors retry at most 3 times with backoff (`core/limits.py`) |
| Context budget | 6,000 estimated tokens, of which 600 for memories; history = current session + last 6 earlier messages |
| Approvals | expire after 15 minutes; holds after 10 minutes |
| Abuse | block after 3 restricted-data attempts (`AgentConfig.block_after_flags`) |
| Live evals | 1 turn per case, at most 4 model calls, `--max-cost` 0.50 USD by default |
| Models | `GEMINI_MODEL`, `GEMINI_READER_MODEL`, `GEMINI_THINKING` (default `low`) |

## Known limitations

- **Single user**, no auth. SQLite with one lock in the web server.
- **The evidence check is a substring match.** It shows the user said something relevant, not that the value is right. Validators cover budget, dates, area and ids.
- **Approval words** are an English/Hinglish list; other languages fall through to the model and simply re-show the card.
- **Input screening is pattern-based.** On blind, model-written attacks it catches about half (round 2: 14/30) with no false positives; the rest reach the model, which refused all 16 misses in round 2. Nothing secret is reachable through any tool, so a miss costs a refusal and a model call, not a leak. Users are blocked by count, not by severity.
- **The judge is a safety net, not a ranking.** It reliably scores bad replies low (calibration), but rated all 90 real replies 5/5 after the fixes, so it can't tell good from great. Long-conversation and Hinglish coverage is 4 conversations and 10 cases.
- **Token budget is estimated** (about 4 characters per token). Gemini's reported counts are logged next to the estimate.
- **Provider events are polled** (every 3 s in the web UI) rather than pushed.
